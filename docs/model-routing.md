# 위험도 기반 모델 라우팅 및 검증 정책 (uijeongbu-lrt-projects)

이 문서는 **의정부 경전철 월간 HTML 분석 보고서 생성 시스템**에서 데이터 분석, 차트 시각화, Jinja2 템플릿 렌더링 시 작업 위험도에 따라 모델 적합성을 사전에 점검하고 사후에 증거 기반으로 검증하는 세부 운영 정책을 정의합니다.

---

## 1. 위험도 3단계 분류 기준

모든 구현·수정 요청은 시작 전에 아래 기준에 따라 위험도를 엄격히 분류합니다.

| 위험도 등급 | 대상 및 작업 범위 | 사전 분석 요건 | 사후 검증 요건 |
| :--- | :--- | :--- | :--- |
| **고위험 (High)** | · 데이터 파이프라인 흐름(`Collector` -> `Analyzer` -> `Jinja2 Renderer`) 계약 변경<br>· 데이터 스키마(`report_data.json`), 차트 시각화 엔진, Jinja2 템플릿 계약 변경<br>· 보안, 외부 API 연동 정책, 데이터 무결성 관련 작업<br>· 원인·해결책의 불확실성이 높은 난제 버그 | **상위 추론 모델 사전 분석 필수** | **상위 검증 모델 사후 검증 필수** |
| **중간 위험 (Medium)** | · 단일 분석 지표 계산 로직 수정 및 보완<br>· 개별 HTML 스타일 및 시각화 차트 옵션 조정<br>· 유틸리티 모듈(`scripts/utils/`) 기능 수정 | 상위 모델 사전 분석 선택 (구현 모델 자체 분석 가능) | **상위 검증 모델 사후 검증 필수** |
| **저위험 (Low)** | · 읽기 전용 데이터/코드 조사 및 설명<br>· 단순 오탈자, 주석, 일반 문서 표현 수정<br>· 실제 보고서 생성 결과에 영향을 주지 않는 순수 서식 정돈 | 사전 점검 보고 생략 가능 | **상위 검증 생략 가능** |

### ⚠️ 위험도 판정 시 주의사항 (승격 및 예외 규정)
1. **데이터 제약 사항**:
   - `data/raw/` 원본 데이터는 수정 불가(Read-Only)이며, 데이터 파이프라인 변환 로직 변경은 즉시 고위험으로 판단합니다.
2. **템플릿 및 차트 수정의 위험도 승격**:
   - 단일 차트 스타일 변경이라도 Jinja2 전체 레이아웃(`templates/design.md`)에 영향을 주는 공통 변경은 **즉시 고위험으로 승격**합니다.

## 2. 작업 전 모델 적합성 점검 (사전 게이트)

- 구현 모델과 검증 모델의 권장 수준을 작업 착수 전에 먼저 판단합니다.
- 모델 적합성 판단을 위한 최소한의 읽기 전용 조사는 수행할 수 있으나, 적합성 판단 전에는 파일을 절대 수정하지 않습니다.
- **고위험 작업 차단**: 고위험 작업은 상위 추론 모델의 사전 분석 없이 실질적인 수정을 시작하지 않습니다.
- 현재 선택된 모델이 요구사항에 비해 낮다고 판단되면 파일 수정 전에 아래 양식으로 선보고하고 지시를 대기합니다:

```text
[모델 적합성 점검]
- 작업 위험도: 높음 / 중간 / 낮음
- 현재 모델: (현재 선택된 모델 또는 모델 등급)
- 권장 구현 모델 수준: 비용 효율형 / 일반형 / 상위 추론형
- 권장 검증 모델 수준: 일반 검증형 / 상위 검증형
- 권장 이유: (예: 데이터 파이프라인 계약 및 Jinja2 템플릿 영향 큼)
- 낮은 모델로 진행할 때 위험: (예: 데이터 파싱 오류 및 렌더링 실패 가능성)
- 권장 선택지:
  1) 상위 모델로 전환하여 분석·구현·검증 진행 (권장)
  2) 현재 모델로 읽기 전용 사전 조사 또는 PoC 분석만 수행
  3) 현재 모델로 진행하되, 실질적인 수정 전 사용자 승인 획득 (Override)
```

- **PoC 격리 원칙**: 선택지 2(사전 조사·PoC 결과)는 참고 자료로만 취급하며, 상위 모델 검토나 사용자 승인 없이 최종 구현·배포에 사용하지 않습니다.

---

## 3. 상위 모델 부재 시 Fallback 및 Override 처리 정책

1. **원칙적 착수 금지**:
   - 자동 모델 전환(handoff)을 지원하지 않는 단일 세션 환경에서 상위 모델을 호출할 수 없는 고위험 작업은 사용자에게 제한 사항과 대체 검증 방법을 보고하고, **사용자의 명시적 지시(Override) 전에는 실질적인 수정을 시작하지 않습니다.**
2. **Override 기록 및 보완 검증 의무**:
   - 사용자가 고위험 작업의 Override를 명시적으로 승인한 경우, **Override 사실과 사유를 작업 진행 로그에 명확히 기록**합니다.
   - Override 작업은 가능한 범위에서 스크립트 실행(`python scripts/generate_report.py`), HTML/PDF 렌더링 확인 및 엄격한 diff 대조를 수행합니다.
   - 상위 검증을 수행하지 못한 작업은 **"상위 검증 완료"로 허위 보고하지 않으며**, "단일 모델 자체 검증 완료(Override)"로 투명하게 기재합니다.

## 4. 검증 모델의 권한 및 책임

검증 모델은 주관적 추측을 배제하고 객관적인 실행 증거를 바탕으로 작업 완료 여부를 판단합니다.

- **금지 권한**:
  - 소스 코드, 원본 데이터(`data/raw/`), 설정 파일 수정
  - Git 커밋, 푸시, 브랜치 조작 등 형상 변경
  - 외부 데이터 쓰기 및 비가역적 파괴 명령 실행
- **허용 권한**:
  - `git diff` 및 변경 내역 조회
  - 시스템 및 분석 실행 로그 조회
  - 보고서 생성 스크립트 실행 (`python scripts/generate_report.py` 등)
  - 생성된 HTML/PDF 산출물 렌더링 및 브라우저 검증
- **임시 산출물 격리**:
  - 검증 명령 실행 중 생성되는 임시 산출물은 사전에 허용된 출력 경로(`outputs/`, `samples/`)에만 생성해야 하며, 소스 코드 및 Git 상태를 오염시키지 않아야 합니다.

---

## 5. 검증 결과 보고 및 재검증 루프 (Verification Loop)

검증 완료 시 아래 표준 형식으로 보고합니다:

```text
[검증 결과]
- 상태: PASS / FAIL / BLOCKED
- 확인 범위: (확인한 파일 목록 및 diff 요약)
- 실행 검증: (python scripts/generate_report.py 실행 결과, 산출물 경로 등)
- 발견 문제: (없음 또는 발견된 결함)
- 심각도: 없음 / 경미 / 치명적
- 권장 조치: (완료 선언 또는 수정 지시)
- 재검증 필요 여부: (Y / N)
```

### 🔄 재검증 루프 (Failure Feedback Loop)
- 검증 상태가 `FAIL` 또는 `BLOCKED`인 경우:
  1. **문제 리포트**: 검증 모델이 실패 로그와 구체적인 결함 원인을 보고
  2. **수정 작업**: 구현 모델이 지적된 결함 부분을 수술적으로 수정
  3. **재실행**: 보고서 생성 스크립트 재실행
  4. **상위 재검증**: 검증 모델이 수정 diff와 실행 결과를 재검증하여 `PASS`를 확인할 때까지 반복
- 모든 결함이 해결되어 최종 `PASS` 판정을 받기 전까지는 작업을 완료로 처리하지 않습니다.
